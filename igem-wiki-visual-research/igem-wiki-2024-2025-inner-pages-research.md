# 2024–2025 iGEM Wiki 正文内页视觉与排版调研

## 范围与结论

本调研实际阅读了 **20 个 2024–2025 iGEM 团队的正文内页**，仅选取 Description、Results、Design、Engineering 等项目内容页，不以首页观察代替正文分析。样本优先覆盖 Grand Prize、Runner-up、Top 10 与 Best Wiki 相关团队；获奖身份以官方竞赛结果页为准。[cite:1][cite:2]

最稳定的共同规律是：高质量 iGEM 正文页并非靠首页式的强视觉取胜，而是以 **双层导航、项目语义化章节、可预测的实验叙事模板、可追溯图文容器** 降低阅读和核验成本。视觉处理应增强“当前读到哪、这一段证明什么、下一步去哪看”，而不是把长文改造成营销落地页。

## 2024 年观察

### 正文结构

2024 样本主要呈现两类结构。GEMS-Taiwan、JU-Krakow、Aachen、Tsinghua 和 Toulouse-INSA-UPS 更强调 **问题—缺口—方案—模块—展望** 的项目叙事；这类结构适合 Description，因为读者先理解为什么需要方案，才能判断设计是否合理。[cite:5][cite:6][cite:8][cite:9][cite:12]

Sydney-Australia、EPFL、WageningenUR 则把正文拆成实验或系统模块。Sydney-Australia 的 Results 目录细至具体实验；EPFL 允许“Unexpected observation”成为独立结果节点；WageningenUR 先列四个系统组件，再逐项解释。这三种做法分别对应结果检索、失败透明度、设计边界表达。[cite:7][cite:10][cite:11]

### 导航与阅读定位

Heidelberg、GEMS-Taiwan、JU-Krakow、Sydney-Australia、Aachen 与 Tsinghua 都有清晰的本页章节入口；Marburg 还加入面包屑和含图标、说明文字的全局栏目导航。结论不是“必须做很复杂的导航”，而是长页必须同时解决两个问题：跨栏目去哪里、当前页面的证据段落在哪里。[cite:3][cite:4][cite:5][cite:6][cite:7][cite:8][cite:12]

### 背景与品牌

Toulouse-INSA-UPS 通过项目名与“月球植物刺激剂”的副标题建立主题记忆，再把正文保持为清晰目录和内容块；Aachen、EPFL、WageningenUR 的白色或近白正文则说明，高质量科研阅读并不要求每一屏都用强背景。项目品牌应集中在 Hero、章节转场与少量图形组件，数据和正文区应优先可读性。[cite:8][cite:9][cite:10][cite:11]

## 2025 年观察

### 目录选型随信息密度变化

2025 样本给出更明确的目录尺度。McGill 采用粘性正文目录；GreatBay-SCIE 使用约 147px 左侧目录；IZJU-China 使用约 250px 的二级工程菜单；Barcelona-UB 使用约 281px 的多层目录；Freiburg 在超长 Results 页提供二级、三级实验树。[cite:13][cite:14][cite:15][cite:19][cite:20]

因此，目录不是统一组件尺寸：章节少且叙事线明确时，可将目录放在正文开头或做成轻量粘性块；系统模块多时，使用 232–288px 侧栏；图表超过 50 张或页面高度超过约 20,000px 时，应升级为可折叠树状目录、URL 锚点和明显的回到顶部入口。这个阈值来自 Freiburg、GreatBay-SCIE 与 IZJU-China 的实际长页观察。[cite:14][cite:15][cite:20]

### 结果与工程页的重复阅读模板

Heidelberg 2025 把 Results 分为 PROCESSING、RESPONDING、SENSING，并在每个模块复用 Aim → 数据 → Discussion；DTU-Denmark 将 Engineering 拆为多轮 DBTL，每轮采用 Background → Design → Build → Test → Learn。重复模板并不单调，反而让评委能快速比较每一轮实验的目标、证据与下一步。[cite:16][cite:18]

Toronto 的跨学科链式叙事则适合将湿实验、软件、伦理、商业化串到同一项目逻辑中；Peking 的面包屑、Contents 与回到顶部适合较传统的文档站路径；SCU-China 证明深色科研页可成立，但必须用更大的衬线正文和清晰 hover / active 状态抵消低亮度背景的阅读压力。[cite:17][cite:21][cite:22]

## 能借鉴的视觉模式

本节只讨论可复用的页面模式，不把原团队的具体视觉资产或项目主题照搬到 CirCure。

### 双层导航

顶栏负责跨栏目，页内目录负责当前页。Description 可采用标题下目录或左侧轻量目录；Results、Engineering、Design 应使用可定位到实验或模块级别的目录。2024 和 2025 的样本都重复出现这种分工。[cite:3][cite:7][cite:13][cite:16][cite:18]

### 叙事型章节

Description 的章节标题应反映项目决策：Problem、Gap、Why this chassis、System、Validation、Safety、Outlook，而不是仅用“Background 1 / Background 2”。GEMS-Taiwan、JU-Krakow、Tsinghua 与 Toronto 都让标题成为叙事节点。[cite:5][cite:6][cite:12][cite:21]

### 总系统先行

Design 页先给系统全景、模块编号或流程图，再进入各模块细节。WageningenUR 的四模块总述、IZJU-China 的系统树尤其适合复杂工程项目：读者在阅读任一局部前，已经知道它在系统中的位置。[cite:11][cite:15]

### 实验叙事模板

Results 统一采用“目标 → 方法或条件 → 图 / 数据 → 解释 → 下一步”。Engineering 统一采用 DBTL。Heidelberg、DTU-Denmark 与 EPFL 的实际页面都表明，真实的异常结果、失败和调整应被作为结构化信息呈现，而不是藏在段落深处。[cite:10][cite:16][cite:18]

### 分流型内容块

Aachen 在项目方案说明后分流到 Wet Lab、Hardware、Education。该模式适用于 Description：当读者已理解方案后，提供 2–4 个“按读者意图”进入深入内容的入口，而不是让所有人继续滚同一篇长文。[cite:8]

### 克制的主题环境

GreatBay-SCIE、IZJU-China、SCU-China 说明强色背景可以形成记忆点；McGill、Peking、Heidelberg 则证明低彩背景更适合长文本。可将高饱和主题色限定在 Hero、章节过渡、目录激活和短结论块，正文使用高对比纸面或半不透明内容层。[cite:13][cite:14][cite:15][cite:16][cite:17][cite:22]

### 图表密集页的树状检索

Freiburg 的超长 Results 页和 Sydney-Australia 的细颗粒度菜单表明，结果页不能只按大章分段。图表、方法、测试和结论都应有稳定锚点；导航支持展开 / 收起，且每个实验块必须有可读标题和摘要。[cite:7][cite:20]

## 可直接落地的前端参数

本节与上节分离：以下是为现有 React / Vite Wiki 设定的建议基线，不是对任一参考队伍 CSS 的逐项复制。

### 布局与宽度

| 场景 | 建议参数 | 说明 |
|---|---:|---|
| 顶部全局导航 | 桌面 `72px`；移动 `56–64px` | 参考样本实际值约 49–95px，多数集中在 56–80px。[cite:13][cite:14][cite:15][cite:16][cite:18] |
| 页级总容器 | `1120–1240px` | 包含目录、正文与旁注的外层最大宽度 |
| 长文正文列 | `680–760px` | 保持阅读行长，不随大屏无限拉宽 |
| 图表 / 流程图列 | `900–1050px` | 仅图表块可突破正文列宽；超宽时水平滚动或响应式缩放 |
| 轻量 TOC | `136–160px` | 适合实验目录或短章节目录 |
| 多层 TOC | `232–288px` | 适合 Design、Results、Engineering 的二级 / 三级导航 |
| TOC 与正文间距 | `32–64px` | 信息层级越深，间距越接近上限 |
| 锚点偏移 | `scroll-margin-top: 88–104px` | 顶部固定导航下仍完整显示标题 |

### 排版与节奏

| 元素 | 建议参数 | 使用原则 |
|---|---:|---|
| H1 | `44–56px`，`700–800`，行高 `1.08–1.18` | 项目名与页面题目可分为两层 |
| H2 | `28–36px`，`700`，行高 `1.2–1.3` | 用章节编号或短标签形成稳定识别 |
| H3 | `20–24px`，`650–700` | 对应实验、模块或决策点 |
| 正文 | `16–18px`，行高 `1.65–1.8` | 深色衬线正文提高为 `18–20px / 1.7–1.9` |
| 图注 | `14–15px`，行高 `1.45–1.55` | 图号、结论、条件 / n / 统计法按固定顺序 |
| 段落间距 | `16–24px` | 不以空行堆出章节感 |
| 主章节间距 | `64–96px` | 在叙事转折、模块切换时取高值 |
| 图表间距 | `32–48px` | 图表密集页避免连续贴合 |
| Callout 内边距 | `16–20px` | 用于结论、限制、异常观察、下一步 |

### 色彩、背景与玻璃表面

| 元素 | 建议参数 | 使用原则 |
|---|---|---|
| 正文背景 | 暖白或低饱和浅色 | 避免纯白大面积生硬感，但不降低文字对比度 |
| 主题氛围层 | `2` 个 `radial-gradient`，不透明度 `0.06–0.10` | 只做低频环境，不进入数据图表区域 |
| 深色正文背景 | 背景亮度约 `20–30%`；正文至少 `#F3F5EE` | 必须有清晰 hover / active / focus 状态 |
| 玻璃表面 | 背景不透明度 `0.82–0.92`；`backdrop-filter: blur(10–14px)` | 仅用于导航、目录浮层、短总结卡；长正文不要重玻璃化 |
| 描边 | `1px` 低对比边框 | 用于图卡与信息容器，不给每个段落加框 |
| 圆角 | 内容卡 `12–16px`；大面板 `18–24px` | 与现有设计 token 一致，避免过度圆润 |

### 动效、滚动与无障碍

| 场景 | 建议参数 | 说明 |
|---|---|---|
| 目录 active 过渡 | `120–180ms` | 色条、背景、文字色变化即可，避免大幅位移 |
| 顶栏压缩 / 背景出现 | `180–240ms` | 页面滚动后改变表面，不改变信息架构 |
| 环境漂移 | `12–20s`，线性或柔和 ease | `prefers-reduced-motion` 下完全静止 |
| 图像 hover | `160–220ms`，缩放上限 `1.02–1.03` | 不让图像放大遮挡图注或邻近内容 |
| 最小点击区 | `44×44px`；回顶建议 `48×48px` | 目录、折叠按钮、返回顶部均适用 |
| 长页阈值 | `>20,000px` 或 `>50` 张图 | 强制提供折叠 TOC、深链、章节进度与回顶入口 |

## 对当前 Wiki 的应用建议

### Description

保持 `Problem → Evidence / Gap → Our Solution → System Modules → Validation → Safety → Outlook → References` 的叙事结构。页面首段应在约 120–180 字内说明目标疾病或问题、底盘或方法、核心方案和价值；在方案解释后插入 2–4 个分流模块，分别通向 Design、Results、Engineering、Human Practices。借鉴 GEMS-Taiwan、Aachen、Tsinghua、Toronto。[cite:5][cite:8][cite:12][cite:21]

### Results

按“实验域 → 实验 → 结论”组织目录。每个实验统一使用 `Aim → 条件 / 方法 → 图表 → Interpretation → Next step`；将负结果、异常观察和模型预测明确标注，不与已验证实验混用。超过图表密度阈值时，升级 `WikiLineSidebar` 为可折叠三级树。借鉴 Sydney-Australia、EPFL、Heidelberg、Freiburg。[cite:7][cite:10][cite:16][cite:20]

### Design 与 Engineering

Design 首屏下先给证据矩阵 / 系统总图，再进入模块；Engineering 以多轮 DBTL 展示每一次决策如何被前一轮结果驱动。页面不需要重复创造强 Hero，主视觉应服务模块定位。借鉴 WageningenUR、IZJU-China、DTU-Denmark。[cite:11][cite:15][cite:18]

### 现有代码策略

优先保留 `WikiPage`、`WikiLineSidebar`、`useWikiPageMotion`、Navbar、Footer 作为唯一页面骨架。优先在 `src/styles/wiki-rebuild.css` 增加栏目级环境层、图注、callout、结论块和目录变体；仅在 `src/components/wiki/wikiPageTypes.ts` 增加真正跨栏目复用的语义 block，例如 `result-summary`、`evidence-note`、`protocol-details`。页面独有互动继续放入 `src/components/wiki/features/`，不要把所有差异塞进万能组件。

不可新增第二套顶栏、Footer 或阅读进度系统；不应修改 Footer 的许可证和 GitLab 仓库链接。图片、字体与脚本最终仍需使用 iGEM 基础设施托管，不能添加外部 CDN。

## 取舍

2024–2025 的高分 Wiki 展示了深色、大色块、白底文档站、侧栏树、正文内目录等不同视觉路线；不存在唯一的“获奖皮肤”。可以归纳的不是颜色，而是：**主题视觉集中于项目身份，正文设计集中于证据可读性，交互集中于定位与状态。**

对 CirCure，Neo-TNBsee 的证据评估、Beth 的故事线、粉色丝带与四类栏目 token 已是足够强的项目语言。最小且高收益的改造是：以栏目 token 生成低对比环境层，统一章节标签和图注，按内容密度调整现有目录，而不是继续增加新的装饰系统。
